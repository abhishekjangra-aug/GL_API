# Gold Loan API Test Harness — Project Reference

Single-file async Python harness that drives the **Augmont Gold Loan (GL) backend** end-to-end through its real REST API. Use it to validate the full GL journey: auth → customer/KYC → appraiser request → ornaments → scheme/eligibility → bank details → ratings → packet sealing → disbursement/documents.

**Read this file first.** It captures the architecture, invariants, and hard-won domain rules so you don't re-analyze `src/maintest.py` (~4500 lines) each time. When a detail here conflicts with the code, the code wins — re-verify with Grep/Read and update this skill.

## Layout & entrypoint

- **`src/maintest.py`** — everything lives here. One class: `GoldLoanApiTest`, driven by an argparse CLI (`main()`). Mode is decided by presence of `--customer`:
  ```bash
  python src/maintest.py                      # DEFAULT: NEW customer -> full create + KYC -> loan -> submit-packet
  python src/maintest.py --customer MS35QNJP  # EXISTING customer by unique id -> new loan (reuses approved KYC)
  python src/maintest.py --partner arvog --amount 550000 --login appraiser
  ```
  No `--customer` → `main()` clears `existing_customer_unique_id` so `run_e2e_test` takes the create-customer + full-KYC path. With `--customer` → resolves that customer and skips KYC if already approved. `--amount` sets `GOLD_LOAN_AMOUNT`. Both modes run the identical end-to-end flow through disbursement → submit-packet → load-loan-details. (The constructor default for `GOLD_LOAN_EXISTING_CUSTOMER_UNIQUE_ID` is now `""` — the bare command creates a new customer, it no longer defaults to MS35QNJP.) **Every run logs in fresh — there is no session/token persistence.**
- **Reference/ground-truth data (do NOT modify): `reference/gold-loan-e2e-flow.har`** — one consolidated HAR of the complete journey (customer/KYC → appraiser → ornaments → scheme → final-loan → bank details → assign packet → ratings → loan documents → partner approval → disbursement → submit packet → load details), 244 API calls. Each entry's `comment` tags its stage (A = customer/KYC/loan/bank/packet/docs, B0 = partner approval, B = disbursement, C = submit-packet/load-details). Merged from four captures, so ids differ across stages — it's a step reference, not one live session. The older per-stage HARs / Postman collection / loan-flow JSON were consolidated into this file and removed.
- Assets (required at runtime, do NOT delete) live in **`assets/`**, resolved via a project-root anchor computed from `__file__` (so CWD-independent): `assets/AADHAR.png` (REAL aadhaar image, 1150x337 — required for KYC upload), `assets/PAN.png`, `assets/scale.jpg` (ornament), `assets/cancelled-cheque-1.png` (bank cheque), `assets/CPV.pdf` (PDF uploads), `assets/dummy_image.png`.
- Generated at runtime (project root): `loan_calc_debug.json` (eligibility diagnostics dump — read this when debugging final-loan-details). **No session/token files are written — session persistence was removed (it caused stale-state bugs, e.g. a restored `random_pan` → "PAN already exists"; every run logs in fresh).**

## The single auth chokepoint

**`_make_authenticated_request(method, api_path, json_data, params, files, headers)`** is the one gateway every endpoint routes through. It:
- Adds the HMAC signature + auth headers.
- **No retry/relogin.** On 401 it raises with a clear message; the run logs in fresh at the start and there is no mid-flight re-login.
- Normalizes the body via `_js_number_normalize` before signing/sending.

Don't add per-endpoint auth or retry logic — change it here.

## HMAC signing (must match the browser byte-for-byte)

- `_generate_signature(api_path, request_body)` signs `json.dumps({**body, "url": path}, separators=(",",":"))` with HMAC-SHA256.
- **Critical:** the server re-serializes JS-style (`JSON.stringify`). Python renders integral floats as `4480.0`/`0.0`; JS renders `4480`/`0`. Mismatch → **401 "auth failed"**. `_js_number_normalize` (classmethod) converts integral floats to ints throughout the body. If you touch numeric fields, keep them int where the server expects int, or the signature breaks. Verify against a Node repro when unsure.

## CryptoJS AES encryption (for aadhaar/PAN numbers AND file paths)

- `_encrypt_identity_proof_number(value)` shells out to **Node** (`subprocess`) using CryptoJS to produce OpenSSL `U2FsdGVkX1...` ("Salted__") ciphertext.
- Passphrase = `CryptoJS.HmacSHA256('TSHZ2_AUGMONT_CY2RG','').toString().substring(0,32)`.
- In `submit_all_kyc_info`, `customerKycPersonal` must encrypt the `identityProof` / `unMaskedIdentityProof` **file paths** (not just numbers) — plaintext paths → "Invalid unMasked Identity Proof file". `customerKycBasicDetails` keeps plaintext.
- **Requires a working `node` on PATH.**

## KYC flow — domain rules learned the hard way

- **Manual-validation fallback:** on the real UI, after aadhaar/PAN auto-verification fails 3×, the system accepts any number. The harness relies on this — it does NOT call `customer-kyc-address` (that endpoint auto-verifies and rejects). `save_customer_address` is **prepare-only**; KYC is submitted via `submit_all_kyc_info` (the manual path).
- Masked aadhaar upload must use the real `src/AADHAR.png` image (via `_upload_file(..., file_path_override=...)`) — a dummy PDF gives "Invalid identityProof file".
- `initiate_kyc` is wrapped by **`_safe_initiate_kyc`** which swallows 400/404 "already submitted/initiated".
- Existing-customer path uses item-level `id` from the appraiser-request list, NOT the nested customer id (that bug caused "Your loan already initiated").

## Existing-customer mode (implemented)

Set `GOLD_LOAN_EXISTING_CUSTOMER_UNIQUE_ID` or `..._ID`. In `run_e2e_test`:
- `_use_existing_customer()` resolves the customer.
- `_existing_customer_kyc_ready()` reads `kycStatus`:
  - **approved** → skip KYC, call `_prepare_loan_fields_from_existing()` (loads master data, fills gender/dob/age/mother_name/signature), go straight to loan process.
  - **not approved** → `_run_full_kyc()`.
- New customers → `add_customer()` + `_run_full_kyc()`.
- **Already-filled info is pulled from the real record, not regenerated.** `get_customer_by_id` (`/api/customer/{id}` → `singleCustomer`) and `get_kyc_customer_detail` (`/api/kyc/get-customer-detail` → `customerInfo`) extract `gender`, `dateOfBirth` (ISO → `dob` via `[:10]`), `age`, `motherName`, and the nested **`customerKycPersonal`** (`profileImage`, `signatureProof`, `martialStatus`, `spouseName`, `identityProofNumber`). `_prepare_loan_fields_from_existing` only generates a value when the record didn't supply it. **Watch for downstream clobbers:** `store_loan_basic_details` used to regenerate `dob`/`age` unconditionally — it must guard `if not self.age or not self.dob` so real values survive. (The nominee name is correctly generated — it's a separate person.)

## Scheme selection & eligibility math (final-loan-details)

This is the most fragile area. Rules verified empirically against captured requests + `loan_calc_debug.json`:

- **Ornaments** (`store_ornament_details`): `net_wt_after_purity = round(net_weight * purity%/100, 2)` — **2 decimals, NOT integer** (integer rounding was a bug). `currentLtvAmount = netWtAfterPurity × goldRate` (real rate via `_fetch_gold_rate`).
- **netWtAfterPurity MUST mirror the server's purity CAP at ltvPercent — this was THE root cause of the persistent final-loan-details eligibility 400.** CONFIRMED from the server's own stored ornaments (`single-loan` on a mismatch): the server recomputes **`nwap = netWeight × min(purityReading, ltvPercent) / 100`** and eligibility = `Σ(nwap × rpg)`. It caps the assessed purity at the ornament's LTV%. Two runs pinned it exactly: run A purity 81.46 < ltv 90 → server kept 81.46; run B purity 91.67 (karat 22/24) > ltv 90 → server capped to 90. Key subtlety: the **ornaments-details response ECHOES our sent `nwap` uncapped** (looks fine), but `single-loan`/final-loan-details use the **capped** value — so you can't detect this from ornaments-details alone. Fix in `store_ornament_details`: `karat_purity = karat/24*100`; `purity% = round(min(karat_purity, float(ltvPercent)), 2)`; `nwap = round(netWeight × purity%/100, 2)`; store that same value as `purityReading` so no further server capping applies. Then our sent `nwap` == the server's recomputed `nwap` to the paisa (verified: 4/4 ornaments, total 549490.26 == server). Prior bugs in this same spot: random `purity` (`uniform(80.1,99.9)`) and karat-only `purity` (91.67, which overshoots the 90 LTV cap) — both 400'd.
- **Partner preference:** only **Roshan Partner** (id 152, schemes 853/861/882, rpg 4533) has a confirmed-accepted `final-loan-details` (200) capture. **ARVOG (partner 10) schemes consistently 400 on final-loan-details** despite structurally-identical, fully-derived requests (tried schemes 792/747/831/727/776 across exposures 0.18–1.02, all rejected) — an undiagnosed partner-level server issue. So `_fetch_partner_scheme_amount` orders candidates by `GOLD_LOAN_PARTNER_NAME` priority (Roshan first) and shuffles only *within* a partner; ARVOG is fallback. If you must use ARVOG, you need an accepted ARVOG capture to find what differs.
- **Partner / scheme / co-lender are CLI-selectable.** A loan has **exactly one partner** — `--partner {roshan|arvog}` → `GOLD_LOAN_PARTNER_NAME` (no "both"). **Roshan Partner** = `ROS-152` (id 152), **Arvog** = `ARV-10` (id 10). `--scheme ID` → `GOLD_LOAN_SCHEME_ID` pins one id (searched in the full candidate list, so it wins even over the catalog pre-check; warns + falls back if not under the partner). **Co-lending** via `--co-lender`: (a) a concrete `NAME|ID` → `GOLD_LOAN_CO_LENDER`; (b) **bare `--co-lender` (argparse `nargs='?'`, `const='__ASK__'`)** sets `co_lender_interactive`, and `run_e2e_test` calls `choose_co_lender_interactive()` right after auth — it fetches `GET /api/co-lender-bank`, prints a numbered menu, reads the pick, and sets `self.co_lender_choice` (so the user needn't remember ids). Either way, `fetch_co_lender_banks` then resolves the choice by exact id or case-insensitive name substring (banks: 4 "DCB bank", 6 "DCB Co lender", 2 "Godrej Bank", 5 "colender added by ops", …), sets `self._forced_co_lender_id`/`self.co_lender_bank_id`, and `_apply_scheme` PRESERVES that forced id (user co-lender wins over the scheme's own `coLenderBankId`). It flows into `check-loan-type` / `final-loan-details` / `generate-interest-table`. Only Roshan-no-co-lending is capture-verified; Arvog & co-lending combos are wired but may 400 at final-loan-details.
- **Scheme candidates** (`_fetch_partner_scheme_amount`): `partner-scheme-amount` returns a list of **PARTNERS** (e.g. Roshan Partner id 152, partnerId `ROS-152`), each with a nested **`schemes[]`** array. The real scheme id / `rpg` / `ltv` / `schemeAmountStart..End` live INSIDE `schemes[]` — you must flatten `partner → schemes[]` into candidates, tagging each with its partner's numeric id. **Do NOT use the partner's own `id`/`rpg` as the scheme** — that was a nasty bug: it sent partnerId `152` as `securedSchemeId`, which coincidentally matched an unrelated scheme #152 (`rpg 4440`, `ltv 74`), so `check_loan_type` "succeeded" but eligibility never matched. The correct schemes under Roshan Partner are 853/861/882 (`rpg 4533`, `ltv 85`). Filter candidates by amount range (`schemeAmountStart ≤ GOLD_LOAN_AMOUNT ≤ schemeAmountEnd`); `check_loan_type` still retries the next on a `"range amount is greater than"` rejection.
- **Catalog pre-check (`fetch_scheme_catalog` + `_scheme_eligibility`):** `GET /api/scheme?partnerType=partner&search=` is the authoritative scheme catalog. Same nested shape as partner-scheme-amount — `{data: [ {id, name, partnerId, rpg, schemes:[...]}, ... ]}`, a list of **PARTNERS** each with `schemes[]`; flatten and index by **scheme id** (the extractor marker must EXCLUDE `rpg` because partner objects also carry `rpg`, else you index by partner id). `_fetch_partner_scheme_amount` calls it after building the sorted candidate pool and drops candidates that fail `_scheme_eligibility`: **inactive** (`isActive` false), **not secured** (`schemeType != 'secured'` — e.g. scheme 218 is unsecured), **amount** outside `schemeAmountStart..End`, or ornament **karat** outside `minKarat..maxKarat` (strings like `"22 K HM"` → parse with `_extract_karat_value`). Best-effort: on fetch failure or empty result, nothing is filtered and `check_loan_type` still validates server-side. **GOTCHA: the catalog's scheme `rpg` (~45000) is ~10× the per-gram rate used for eligibility (~4533 from check-loan-type's `securedScheme.rpg`). NEVER use catalog `rpg` for eligibility — the pre-check only reads active/secured/karat/amount, never rpg.** All catalog schemes have `isCustomerDisplay: false`, so that flag is not a usable filter.
- **`check_loan_type`** captures, from `data.securedScheme`: `ltv` → `self.secured_ltv` AND **`rpg` → `self.secured_rpg`** (the scheme's loan rate/gram, e.g. 4440). `createdBy` = `logged_in_user_id`.
- **Eligibility (`get_final_loan_details`) = `netWtAfterPurity × scheme rpg`. CONFIRMED against a real accepted (200) capture** (`fic flow.har` → `final-loan-details`: scheme 853 rpg 4533; each `loanAmount = ornamentsCal × 4533`; `totalEligibleAmt = Σ loanAmount = 653749.26`; the harness reproduces this to the paisa). So: per ornament `ornamentsCal = netWtAfterPurity`, `rpg = self.secured_rpg` (the SELECTED scheme's rpg), `loanAmount = round(nwap × schemeRpg, 2)`; `totalEligibleAmt = Σ loanAmount`; `loanFinalCalculator.securedRpg` = that same scheme rpg. Do NOT apply LTV (the scheme rpg already bakes it in) and do NOT use `currentLtvAmount`/valuation.
  - **`eligible must be ≥ finalLoanAmount`** — the accepted capture had eligible 653749 > loan 400000. If ornaments are too small, eligible < loan, `finalLoanAmount` gets capped, and it 400s. `store_ornament_details` therefore fixes **4 ornaments** and sizes gross weight to the target loan (`GOLD_LOAN_AMOUNT × 1.3 / rpgFloor(4000) / purity(0.9)`, ±15% each) so eligibility clears the loan with headroom.
  - **ALL `loanFinalCalculator` financial fields must come from the server, NOT be hardcoded.** The accepted capture's `processingCharge`/`securedprocessingCharge` (4000), `interestRate` (1), `securedExposure` (=`posExposureAgainstScheme`, 0.18), `tenure` (6), `upfrontInterestAmount` all come from the **check-loan-type** response `data`; `securedRebateInterest` (2) and `totalFinalInterestAmt` (=`totalInterestAmount`, 24000) come from **generate-interest-table** `data`. The server recomputes the loan with the scheme's real charges/interest/tenure and 400s (with the SAME misleading "total eligible" message) if the calculator contradicts it. `check_loan_type` captures these into `self.tenure_months/interest_rate/secured_processing_charge/upfront_interest_amount/secured_exposure/loan_start_date/loan_end_date`; `generate_interest_table` captures `secured_rebate_interest`. The captured `tenure` must also drive `generate_interest_table`'s request so the schedule matches.
  - **History (why this took so long):** the SAME 400 message was thrown by THREE different bugs that each masked the formula — empty interest table (data-wrapper), mixed-karat ornaments (scheme summed a subset), and too-little-gold (eligible<loan, capping). Each made `nwap × schemeRpg` *look* wrong, sending me chasing `valuation` and `valuation × LTV` (both actually wrong). Lesson: when an eligibility 400 persists, rule out interest-table/karat/weight BEFORE touching the formula — and get a 200 capture early instead of inferring.
- **The SAME 400 message ("total eligible amount doesn't match the calculated amount") has THREE independent causes — check ALL:**
  1. `totalEligibleAmt` wrong (scheme rpg issues above).
  2. **Empty/zero interest schedule.** `generate-interest-table` returns `{"data": {"interestTable": [...], "totalInterestAmount": N}}`. `generate_interest_table` must read from `data` (reading the top level silently drops it → `interestTable: []`, `totalFinalInterestAmt: 0`). final-loan-details needs a populated `interestTable` (pass the rows straight through — same shape) and `totalFinalInterestAmt = totalInterestAmount` (= Σ per-month `securedInterestAmount`).
  3. **Karat mismatch between ornaments and the scheme.** Each scheme has a `minKarat`..`maxKarat` range (e.g. `22 K HM`..`24 K`). The server computes eligibility over only the karat-ELIGIBLE ornaments, so if a randomly-generated 19K/20K ornament falls outside the scheme's range, the server's total (subset) ≠ ours (all ornaments) → the same 400. Fixes: `store_ornament_details` uses **ONE karat for all ornaments in a run** (biased to 22K, the most broadly covered), and `check_loan_type`'s retry loop is **karat-aware** — it rejects a scheme whose `minKarat..maxKarat` doesn't cover every ornament karat and tries the next candidate. `_extract_karat_value` must parse the LEADING integer via regex (`re.search(r'\d+')`) — a naive `.replace('K','')` returns 0 on `"22 K HM"` and silently disables the check.
- **Mismatch diagnostic (`get_final_loan_details`):** on a 400 whose message contains "eligible amount", the harness `GET`s `single-loan` and logs the server's stored `nwap`/`currentLtvAmount`/`totalEligibleAmt` vs what we sent (`single_loan_on_mismatch` in the debug dump), then re-raises. It does **NOT** re-submit single-loan's `totalEligibleAmt` — for an in-progress loan that value is the **valuation** (`Σ currentLtvAmount = Σ nwap×goldRate`, ~1.66M), NOT the rpg-based eligible final-loan-details wants (~610k), so echoing it just 400s again (that mistake once turned 1 failure into 2). The valuation-vs-rpg distinction: `ornaments-details` response `totalEligibleAmt` = **valuation**; final-loan-details expects **`Σ nwap×rpg`**.
- `_dump_loan_calc_diagnostics()` writes `loan_calc_debug.json` — the ground truth. Key fields: `check_loan_type_response.data.securedScheme` (`rpg`, `ltv`, `schemeAmountStart/End`), `ornaments_details_response.ornaments[].netWtAfterPurity`, `generate_interest_table_response.data.interestTable`. Always inspect it when final-loan-details 400s.
- **Many loan-process responses are wrapped in a `data` object** (`check-loan-type`, `generate-interest-table`, etc.). Always read `resp_json['data']` — reading the top level returns `None`/`[]` and fails silently.

## Bank details & verification

- **`validate-account` (penny-drop) MUST run BEFORE `bank-details`** — otherwise bank-details 400s with "bank details is not verified". HAR order: GET bank-details → GET account-details-karza (IFSC lookup only, not verification) → POST validate-account → POST bank-details. `validate_account` runs in the Bank-Details step (not the later disbursement step).
- **The SBI test account penny-drop VERIFIES** — CONFIRMED from a real validate-account call with `00000036150491589`/`SBIN0011777`/`LIC MUTUAL FUND`: response `data.bankTxnStatus: true`, `isVerified: true`, `isManuallyVerified: false`. So the failure was NEVER the account — it was purely running validate-account AFTER bank-details. With the reorder, `validate_account` captures `bankTxnStatus` into `self.bank_account_verified` and `store_bank_details` sends the confirmed system-verified flags: `isVerified: true`, `isManuallyVerified: false`, `manualVerifiedStatus: ""`.
- **`toBePaid` MUST equal `finalLoanAmount − processingCharge − upfrontInterestAmount`** — else bank-details 400s with **"To Be Paid amount is incorrect"**. Do NOT hardcode it. `processingCharge`/`upfrontInterestAmount` are scheme-specific and captured from **check-loan-type** (`data.securedprocessingCharge` = `max(processingChargeFixed, processingChargePercent% × amount)`; `data.upfrontInterestAmount`), stored in `self.secured_processing_charge`/`self.upfront_interest_amount`. `store_bank_details` computes `to_be_paid` and sets `toBePaid`, `availableLimitForDisbuserment` (= toBePaid), `processingCharge`, and `actualProcessingCharge` from these. Confirmed against a 200 capture: final 400000, procCharge 4000 → toBePaid 396000. A scheme with 0 processing charge → toBePaid = finalLoanAmount.
- **Do NOT trust the validate-account `message` field** — it can read `"Something went wrong"` even on a fully successful verification (`bankTxnStatus: true`). Rely on `bankTxnStatus`, not `message`.
- **Manual fallback (rarely used):** if `bankTxnStatus` is false/absent, `store_bank_details` sends `isManuallyVerified: true` + `manualVerifiedStatus: "verified"` (best-guess string, no captured manual example). Since the SBI account verifies for real, this path normally won't trigger. Passbook proof is a cheque PNG image (`CHEQUE_IMAGE_PATH`), not a PDF; `passbookProofImageName` is `[]`.

## Packet creation, assignment & sealing

- **There is no "assign-packet" endpoint** — assignment is embedded in `add-packet-images` via `packetOrnamentArray: [{packetId, ornamentsId, packetsName, ornamentsName}]`.
- **Packet create + assign require ADMIN — the rest of the loan runs as the appraiser.** `add_packet_images` captures the appraiser's `logged_in_user_id`, swaps `self.auth_token` to an admin token via `_admin_token()` (mobile **8880008880**, OTP **1234**, `user-send-otp` → `auth/verify-login`; does NOT persist state), runs create+assign, then restores the appraiser token before sealing. `_admin_token` mutates only `self.auth_token` (not branch/user-id/saved state), so `internalUserBranch` stays the appraiser's branch (1), matching the real calls.
- **`create_packet` (POST /api/packet, admin)** — Body: `{id:null, packetUniqueId:UNIQUE, internalUserBranch:<branchId>, appraiserId:null, auditorId:null, barcodeNumber:UNIQUE, userType:"", isNewPacket:false}` where **`barcodeNumber == packetUniqueId`**, a single random value (e.g. `pac-<8 digits>`). Response is only `{"message":"you adeed packet successfully"}` (sic) — **no id**.
- **`assign_packet` (PUT /api/packet/{id}, admin)** — binds the packet to the appraiser: same body as create but with the real `id`, `appraiserId: <loan's appraiser user id>`, and **`userType: "appraiser"`** (create used `""`). Response `{"message":"packet updated successfully"}`. Without this the packet stays unassigned and sealing can't proceed.
- **Resolve the numeric id from the listing** (`_find_packet_by_unique_id`): `GET /api/packet?from=1&to=N` returns `{packetDetails:[...], count}`, newest first, so a just-created packet is on page 1. Match on `packetUniqueId`/`barcodeNumber` to get its `id` (e.g. 10394) for both the assign PUT and `packetOrnamentArray.packetId`. `available-packet?masterLoanId=` may not surface a brand-new packet, so the listing is the reliable id source; `add_packet_images` falls back to `fetch_available_packet` only if the created packet can't be resolved.
- **`add-packet-images` body — CONFIRMED against the assign-packet HAR:** the body carries **`loanAmountDigi`** (string, 2dp, e.g. `"400000.00"`) and **omits** `createdBy`/`internalBranchId`. `packetOrnamentArray[].packetId` is the packet's numeric id (as a string); `packetsName`/`ornamentsName` are the packet unique id + comma-joined ornament names. Response `{"message":"Packets added successfully"}`. Admin create/assign **seeds the pool**: the HAR's `available-packet?masterLoanId=` returns the exact packet an admin assigned earlier (e.g. 10394 / pac-12341234, appraiserId 1473), so a run can either admin-create fresh or reuse an available pool packet.
- **After sealing, lock the stage:** `POST /api/loan-process/update-loan-lock` `{masterLoanId, loanStageId: 8}` → `{"message":"Success"}`.

## Role-based ratings (each rating runs under a different login)

The GL flow hands the loan between roles. Static OTP **1234** for all; each role logs in via `_role_token(login_type)` (send-otp → verify-login) which returns a token WITHOUT persisting/mutating session state — the caller swaps `self.auth_token`, runs the role call, and restores the appraiser token in a `finally`. Mobiles: **admin 8880008880** (packet create/assign), **appraiser 8880008881** (main actor + `add_appraiser_rating`), **ops 8880008882** (ops rating / final approval), **bm 8880008883** (BM approval).

- **Appraiser rating** (`add_appraiser_rating`, `/api/loan-process/appraiser-rating`) — the appraiser's own submission, runs on the appraiser token; no swap.
- **BM rating is CONDITIONAL: only when loan amount > 5L** (`BM_RATING_THRESHOLD = 500000`). `submit_bm_rating_if_required` checks `final_loan_amount`, and if over threshold swaps to the **bm** token before `add_bm_rating` (`/api/loan-process/bm-rating`). At/under 5L it's skipped entirely.
- **Ops rating** (`submit_ops_rating` → `add_ops_rating`, `/api/loan-process/ops-rating`) — final approval, always runs under the **ops** token. `loanAmountDigi` uses the real `final_loan_amount`.

## Upload documents (`store_loan_documents`)

`POST /api/upload-file?reason=loan&loanId={masterLoanId}` × 3 (loan agreement, pawn copy, scheme confirmation PDFs, multipart `avatar`) + `POST /api/upload-file?reason=customerIncomeGeneratingDocument&customerId={customerId}` × 1 → then `GET /api/lead/lead-converter` → `POST /api/loan-process/loan-documents`. The loan-documents body reuses earlier KYC artifacts (`signature`, `panImage`, encrypted `identityProof`/`unMaskedIdentityProof`, `panCardNumber`) plus `consumptionSupportingDocs:[{path:<income doc>}]`, `loanAmountDigi`, `loanType:"Fresh Loan"`. Response `{"message":"Success", masterLoanId, loanId}`.

## Disbursement (partner login) & submit packet (appraiser)

After ops rating the loan is disbursed, then the packet is handed to the partner branch to complete it.

- **Disbursement runs under the PARTNER login** — `partner` = **8767002003** (OTP 1234, Roshan, JWT id 1391). `disburse_amount` swaps to the partner token (via `_role_token("partner")`), then: `update-loan-lock` → GET `disbursement-loan-bank-detail?loanId&masterLoanId` → `validate-account` (penny-drop re-run) → **partner approval** → POST `partner-wise-disbursement`, and restores the appraiser token in `finally`.
- **Partner approval, immediately before disbursement** (`_partner_disbursement_status`, from `partner approval.har`): POST `/api/loan-process/partner-disbursement-status` with the partner signing off — `applicationFormForPartner:true`, `goldValuationForPartner:true`, `loanStatusForPartner:"approved"`, plus the other roles' flags, `loanId`/`masterLoanId`/`loanAmountDigi`/`partnerId`(152)/`loanType:"Fresh Loan"`/`checkPointers:{}`. Response `{"message":"success"}`. Runs inside the partner-token block, right after validate-account.
- **Source the disbursement body from `disbursement-loan-bank-detail.data`** (`fetch_disbursement_bank_detail`) — it carries `finalLoanAmount`, `securedLoanAmount`, `securedLoanUniqueId` (AUGM-…), `securedSchemeName`, `securedLoanId`, `userBankDetail` (customer bank), processing charges, etc. `partner-wise-disbursement` echoes these plus transaction fields: `securedBankTransactionId` (random 15-digit UTR), `securedAmountDisbursedByBank`, `paymentMode:["bank"]`, `bankArray:[{disbursementStatus:"Disbursed to Customer", ...bank}]`, `bankTransferType:"neft"`, `penalInterest:2`, `paymentGatewayId:5`, `partnerId` (152), `actualProcessingCharge` (≈ month-1 secured interest). Response: `{"message":"Your loan amount has been disbursed successfully", data:{interestTable}}`.
- **Submit packet runs as the APPRAISER** (`submit_packet`): `update-loan-lock` → GET `packet-tracking/view-packets?masterLoanId` (→ barcode + packetUniqueId) → GET `packet-location` list → GET `packet-tracking/get-particular-location?packetLocationId=4&masterLoanId` (→ partnerId/name) → GET `packet-tracking/user-name?mobileNumber=…&receiverType=PartnerUser&partnerBranchId=…` (→ partnerReceiverId + name) → POST `partner-user-otp/send-otp` `{mobileNumber, id:<appraiserId>, type:"updateLocationCollect", masterLoanId}` → POST `partner-user-otp/verify-otp` `{otp:"1234", referenceCode, type:"updateLocationCollect"}` → POST `packet-tracking/submit-packet-location`. Response: `{"message":"packet location submitted"}`.
- **Submit-packet env constants** (Roshan partner collection point, hard to derive — hardcoded from the HAR): `PACKET_LOCATION_ID="4"`, `PARTNER_USER_MOBILE="8652849318"` (roshan ghadge, id 170), `PARTNER_BRANCH_ID="146"`. `submit-packet-location.barcodeNumber` is `[{Barcode:<UPPER>, packetId:<lower packetUniqueId>}]`.
- **`loanUniqueId` (AUGM-…) is assigned at the ASSIGN-PACKET stage**, not at disbursement. It's carried in `single-loan.data.loanUniqueId`; since `add_packet_images` calls `fetch_single_loan`, capture `self.loan_unique_id` there. Disbursement's `securedLoanUniqueId` is only a fallback. This id feeds the disbursement body and the final loan-details search.
- **Load loan details (final step, `fetch_loan_details`)** — GET `/api/loan-process/loan-details?from=1&to=25` (list) then the targeted search `&loanUniqueId=<AUGM-…>`; `data[0]` is the full loan record. Display fields: `loanStage.name` (**"packet submitted" / id 13 = process complete**), `finalLoanAmount`, `tenure`, `loanStartDate`/`loanEndDate`, `customer` (name/uniqueId/mobile/PAN via `customer` + `customerLoan[0].loanUniqueId`), `appraiser`. A completed run ends at loanStage 13.

## Full E2E order (`run_e2e_test`)

Authentication → (Create Customer **or** Load Existing Customer) → KYC Process → Appraiser Request & Loan Basics (`create_appraiser_request`, `track_loan_history`, `fetch_max_loan_limit`, `store_loan_basic_details`, `store_nominee_details`, `store_ornament_details`) → Scheme/Balance/Loan-Type (`check_loan_type`, `get_interest_rate`, `generate_interest_table`, `get_final_loan_details`) → **Bank Details** (`fetch_bank_details`, **`validate_account`**, `store_bank_details`, `add_appraiser_rating`) → **Assign Packet** (`add_packet_images`, `update_loan_lock`) → **BM Rating if > 5L** (`submit_bm_rating_if_required`, bm login) → **Upload Documents** (`store_loan_documents`) → **Ops Rating** (`submit_ops_rating`, ops login) → **Disbursement** (`disburse_amount`, partner login 8767002003 — includes `_partner_disbursement_status` partner approval right before `partner-wise-disbursement`) → **Submit Packet** (`submit_packet`, appraiser — completes the loan) → **Load Loan Details** (`fetch_loan_details`, search by loanUniqueId + display; ends at loanStage 13 "packet submitted").
